CENTRAL PLANNER DESKTOP BLUEPRINT AUDIT
=======================================

Audit date: 2026-08-07
Audited file: desktop/BLUEPRINT.html
Basis: Current working tree, including the dashboard implementation, server/event
contracts, launchd configuration, and current Electron documentation.

VERDICT
-------

The blueprint should not yet be treated as build-ready. The overall direction is
strong—attach-first, no renderer privileges, launchd ownership, and an attach-only
fallback are sensible—but there are eight blocking contradictions and a substantial
second tier of reliability, security, packaging, and testing gaps.


BLOCKING FINDINGS
-----------------

1. The notification mapping does not match the server's actual event contract.

   Blueprint reference: desktop/BLUEPRINT.html:241-242

   The blueprint says session:status carries question and handoff. It does not.
   Claude and Codex store those fields through updateTask(), which emits task:update;
   their subsequent session:status payloads contain status, tokens, cost, error, and
   authNeeded, but no question or handoff.

   Implementation references:
     - app/lib/sessions.js:1235-1262
     - app/lib/sessions.js:1601-1617
     - app/lib/taskStore.js:171-199

   As written, Phase 1 would silently miss two of its five headline notification
   types.

   The real mapping must distinguish:
     - Approval: session:permission
     - Question/handoff: transitions in task:update
     - Turn failure: session:status.error
     - Failed-turn authentication: session:status.authNeeded
     - Proactive Claude sign-out: auth:status
     - Proactive Codex disconnection: provider:status

2. The notification channel is lossy, but the blueprint treats it as durable.

   WebSocket events have no sequence numbers, acknowledgement, replay, or event
   journal. A reconnect receives a state snapshot, but pending permissions are absent
   from that snapshot: activeSessions() contains only session status, agents, and
   edits (app/lib/sessions.js:1792-1800). Failures are not persisted as notification
   events either.

   Consequences:
     - An approval or failure occurring during sleep, a half-open socket, or reconnect
       backoff can be missed forever.
     - Questions and handoffs can be recovered from task state, but the blueprint does
       not define snapshot reconciliation or persistent "already notified" state.
     - A newly launched shell cannot reconstruct an already-pending approval.
     - "De-dupe by requestId/task" is too vague: de-duping by task would suppress
       legitimate later turns.

   Reliable "Claude needs you" notifications require either a persisted attention/
   event model in app/, or explicit best-effort semantics. The present zero-app-change
   design cannot guarantee delivery.

3. The advertised atomic spawn safety is impossible with the proposed architecture.

   Blueprint references: desktop/BLUEPRINT.html:213-218, 332, 461-465

   The actual sequence is:

     check launchd -> check port -> spawn Node -> Node initializes -> Node binds

   Another process—or launchd itself—can bind during that gap. No user-space preflight
   check can reserve a port for a different process.

   The stderr watch only detects the collision after the new server has already
   executed artifact watchers, auth checks, orphan sweeps, and the task-status rewrite
   the design is specifically trying to prevent.

   Implementation references:
     - app/server.js:1099-1142
     - app/server.js:1144-1169
     - app/server.js:1171-1177

   The gates reduce probability; they do not establish invariants I1/I2. A true
   guarantee needs the server to bind before side effects, exit on bind failure, or
   accept a socket reserved by the parent—all of which require an app/ change.

4. Packaged repo-root discovery will fail in the normal packaged app, not merely
   after relocation.

   Blueprint references: desktop/BLUEPRINT.html:260-262, 617

   Electron Packager copies the desktop application under:

     Central Planner.app/Contents/Resources/app

   or app.asar. Therefore __dirname/.. points into Contents/Resources, never to the
   source repository—even if the packaged output remains inside the repo.

   CP_REPO is not a practical Finder-launch escape hatch because Finder-launched apps
   do not normally inherit terminal-only environment variables. The spawn fallback is
   therefore expected to fail in the actual packaged daily driver unless the repo path
   is embedded at build time or persisted/configured elsewhere.

5. Close-to-hide and the proposed draft guard cannot work together as described.

   Blueprint references: desktop/BLUEPRINT.html:220-222, 252-254, 553-556

   Electron emits the BrowserWindow close event before DOM beforeunload. If the close
   handler prevents closing and hides the window, there is no unload, so
   will-prevent-unload never fires. If closing is allowed to continue, the window is
   destroyed rather than hidden.

   This makes the Day-1 Cmd+W acceptance criterion impossible as written.

   The coherent behavior is likely:
     - Close hides without prompting because nothing is lost.
     - Reload and actual quit invoke the draft guard.

6. Owned-child quit directly contradicts the browser/PWA invariant.

   Blueprint references: desktop/BLUEPRINT.html:149-159, 220-222, 482-493, 580-583

   The mission says the browser and phone keep working "at all times," and invariant
   I8 says their behavior is unchanged before, during, and after the shell runs.

   But in child-owned mode, Cmd+Q intentionally kills the only server. Every browser
   and phone client then stops working.

   I8 is valid only for attached mode. Either narrow the invariant or leave an owned
   server alive after shell quit.

7. The lifecycle needs serialization and intentional-exit semantics.

   Reconciliation can be triggered by startup, did-fail-load, power resume, FAILED
   retry, and child exit. Nothing states that these paths share one single-flight
   coordinator, generation token, or cancellation mechanism.

   Without that, two loops can race through the spawn gates and create two children.
   There are also dangerous re-entry cases:
     - A readiness timeout kills the child; its exit handler may immediately begin
       another spawn.
     - EADDRINUSE cleanup can trigger the generic child-death recovery path.
     - Cmd+Q can kill the child and provoke a respawn while the app is quitting.
     - A stale loop using the former port can outlive a newer loop.

   The state machine needs explicit expectedExit, quitting, one active reconcile
   operation, cancellation, and idempotent terminal transitions. This is essential to
   the one-server guarantee, not a mere implementation detail.

8. Notification clicks normally cannot reach the named project.

   Blueprint references: desktop/BLUEPRINT.html:240-242, 509-511

   The blueprint says a click focuses an existing window, while #project is applied
   only when creating a new window. Because close hides rather than destroys, an
   existing window will almost always exist.

   The frontend only reads the hash during initialization
   (app/public/app.js:10240-10253); it has no runtime hash-change route. Thus a
   notification click will usually focus whatever project/task was previously visible,
   not the project that needs attention. This contradicts the "one click to the right
   project" claim.


HIGH-PRIORITY PROBLEMS
----------------------

9. Quit protection covers too little work.

   The confirmation counts only tasks whose last snapshot says running. Stopping an
   owned server can also terminate:
     - A long file run
     - A LaTeX build
     - Claude Fix
     - A Codex/Claude turn missed by stale state
     - Authentication or update activity
     - Work initiated from another browser or the phone

   The state snapshot already exposes sessions, runs, jobs, and texfix
   (app/server.js:104-123). The quit decision should use all active work, not task
   records alone.

   Risk R8's statement that a stale snapshot can cause only a "needless or missing
   dialog, never data loss" is too strong. Killing an external script during a write
   can lose or corrupt work; it can certainly lose billed computation and time.

10. The permission policy is incomplete and grants an unused permission.

    Blueprint reference: desktop/BLUEPRINT.html:224-226

    The design mentions only setPermissionRequestHandler and allows any request for
    clipboard write or fullscreen. Complete Electron permission handling requires
    both setPermissionCheckHandler and setPermissionRequestHandler.

    It must also validate:
      - The requesting origin is exactly the dashboard origin.
      - The request comes from the intended main webContents.
      - The request is from the main frame, not an artifact iframe.
      - Clipboard is the specific required operation.

    I found no fullscreen use in the dashboard, so allowing fullscreen violates the
    document's own least-privilege posture.

11. did-fail-load recovery is dangerously under-specified.

    The dashboard contains multiple artifact iframes. Electron reports frame-load
    failures with an isMainFrame distinction. A missing/deleted artifact can therefore
    produce did-fail-load; an unfiltered handler could replace the whole dashboard
    with the connecting splash.

    It must ignore:
      - Subframe failures
      - ERR_ABORTED and canceled/superseded navigation
      - Draft-vetoed reloads
      - Expected transitions to connecting.html
      - Failures from stale lifecycle generations

    This needs an explicit acceptance test.

12. The notifier's state model remains underspecified even after fixing event names.

    It needs clear rules for:
      - Event identity: permission request ID or task + event type + completed-turn
        number
      - Persistent last-notified state across shell restarts
      - Closing an approval banner on session:permission:resolved
      - Multiple approvals from the same task
      - Repeated identical errors on different turns
      - Snapshot reseeding after reconnect
      - Whether an old, still-unanswered question should notify after shell restart

    "De-dupe by requestId/task" is not sufficient.

13. The main-process WebSocket lacks half-open detection.

    The renderer closes a socket after 60 seconds without the server's 25-second tick
    (app/public/app.js:1707-1720). The proposed notifier only reconnects on close/error
    and force-kicks on system resume.

    A network transition that does not generate powerMonitor.resume can leave the
    notifier socket apparently OPEN forever. It should copy the renderer's
    last-message/tick watchdog.

14. Focus suppression is broader than its rationale.

    The text says suppression prevents notifications while Graham is "watching the
    very task," but the implementation criterion is only window.isFocused(). A focused
    window might be on the overview, another project, Settings, or another task.

    At minimum, main can parse the current project hash. Task-level accuracy needs a
    real routing/visibility bridge.

15. The claimed list of three cross-folder couplings is far from complete.

    Blueprint references: desktop/BLUEPRINT.html:276-278, 482-493

    The shell also depends on:
      - WebSocket event names and payload schemas
      - Initial state snapshot schema
      - Pending-attention persistence
      - local.projectmanager launchd label
      - Server entry point and working directory
      - EADDRINUSE log wording
      - Server startup ordering and signal behavior
      - Hash routing
      - Cmd+0..5 behavior
      - beforeunload behavior
      - Manifest route and identity
      - Node version requirement
      - Provider/auth status events

    The notification error in finding 1 is direct evidence that these interfaces are
    not safely captured by the current three-coupling claim.

16. A packaged shell can become permanently version-skewed from the server.

    The dashboard's Update button updates the repository/server, but it does not
    rebuild or replace the packaged Electron app. After an app/ update, an old shell
    may continue expecting former WebSocket payloads and routing behavior.

    Phase 5 can defer automatic updates, but Phase 1 still needs a version-
    compatibility policy and an explicit "repack after these changes" rule.

17. The signing contract is contradictory and incomplete.

    The app is described as "unsigned, ad-hoc," while code signing is deferred to
    Phase 5. An ad-hoc signature is still a code signature. Electron states that
    unsigned macOS applications emit notification failures rather than displaying
    notifications; System Settings cannot repair a signing failure.

    Phase 1 should specify:
      - Exact Packager signing options/identity
      - codesign --verify --deep --strict acceptance
      - A listener and durable log for Notification's failed event
      - Separate handling for signature failure versus user-denied notification
        permission

18. Port resolution does not actually mirror app/lib/config.js.

    The app can locate config.json through CP_ROOT (app/lib/config.js:21-24). The
    shell's proposed precedence ignores CP_ROOT and assumes repo-root configuration
    (desktop/BLUEPRINT.html:264-266).

    It also lacks validation for CP_PORT/config values: integer, finite, and in
    1..65535.

    A runtime port change is not truly recovered while a healthy-but-stale SPA remains
    loaded: its HTTP and WebSocket calls continue targeting the old origin, and no
    main-frame load failure occurs until the user reloads. Changing ports also creates
    a new browser origin, causing another localStorage reset—contradicting the
    "one-time" language.

19. A shell crash can orphan an owned server permanently.

    Normal quit kills the child, but a main-process crash or forced termination skips
    that cleanup. On the next launch, the surviving server is classified as external,
    and the no-adoption rule means the shell will never own or stop it. Loading launchd
    later then produces exactly the occupied-port zombie scenario described in R6.

    Cutting unsafe PID adoption is reasonable, but the remaining orphan behavior must
    be explicit, diagnosable, tested, and have a safe manual recovery path.

20. The manifest identity check identifies the product, not the intended instance or
    protocol version.

    Any Central Planner checkout—or any process returning the same JSON name—passes.
    There is no compatibility/API version check. That becomes more dangerous once
    packaged shell and server versions can drift independently.


SPECIFICATION AND DELIVERY WEAKNESSES
-------------------------------------

21. No actual Electron version is pinned in the binding blueprint.

    The document says there are no unresolved choices, then specifies only "current
    stable >=35." As of the blueprint date, the current stable release is 43.3.0. The
    exact tested version should be in the blueprint before its API assertions are
    binding.

22. Packaging is not reproducible enough.

    The proposed tree omits package-lock.json, and only Electron—not
    @electron/packager—is explicitly required to be exact. Packager also normally
    emits:

      <out>/<name>-darwin-<arch>/<name>.app

    not dist/Central Planner.app. That acceptance path needs a packaging script that
    deliberately produces it.

    "npm ls --all shows no runtime deps" is also the wrong assertion: it will show dev
    dependencies and their transitive trees. npm ls --omit=dev or package.json
    inspection is the relevant check.

23. There is no persistent main-process log.

    The child server log is specified, but shell lifecycle decisions, dropped URL
    schemes, notification failures, probe classifications, launchctl results, and
    crash diagnostics otherwise go to a Finder-launched process's disappearing
    console. A main log with size bounds/rotation is necessary. spawned-server.log
    also has no rotation policy.

24. Window-bounds persistence lacks off-screen recovery.

    Saved bounds must be validated against current displays and constrained to a
    visible area. Otherwise disconnecting a monitor can make the "single existing
    window" impossible to find. Atomic/corruption-safe writes, debouncing, and
    maximized/fullscreen handling are also unspecified.

25. Shipping a known-dead mic control undermines the Day-1 daily-driver claim.

    The button will present a misleading "allow microphone" message even though
    granting permission cannot repair Electron speech recognition.

    Implementation references:
      - app/public/app.js:8161-8162
      - app/public/app.js:8223-8230

    Documentation does not make a visibly broken primary control acceptable. This is
    a strong argument against treating "zero app/ changes" as more important than
    product correctness.

26. The automated test plan covers only the easiest layer.

    Missing automated or deterministic coverage includes:
      - WebSocket notification mapping and snapshot reconciliation
      - De-dupe/cancellation
      - Half-open notifier recovery
      - Concurrent lifecycle triggers
      - Intentional versus unexpected child exits
      - Quit while a run—not a task—is active
      - Repo-root resolution in a packaged layout
      - Port parsing and CP_ROOT
      - URL policy, redirects, and permission-origin checks
      - Main-frame filtering for did-fail-load
      - Off-screen bounds recovery
      - Package signature verification and package contents

    The proposed "large /api/state fetch" is not a reliable way to simulate a blocked
    event loop. A controlled stub or temporarily SIGSTOPped test server would exercise
    timeout-plus-TCP-acceptance deterministically.

27. The three-day estimate is not credible for the full contract.

    Attach-only, window/menu behavior, and a best-effort notifier may fit. The child-
    spawn supervisor, safe asynchronous quit, signing/notification validation,
    recovery state machine, and adequate tests do not fit comfortably once the
    contradictions above are resolved.

28. The contract-governance story can drift.

    BLUEPRINT.html calls itself binding, while a later CONTRACT.md will become the
    review gate. Two manually maintained normative documents will diverge. The
    D1/D2/D3 and C1/C2 source designs/critiques are also absent from the repository, so
    the appendix's provenance cannot be independently reviewed.


BOTTOM LINE
-----------

The cleanest viable Phase 1 is the attach-only shell the blueprint already identifies
as independently useful. That preserves the window, dock identity, unthrottled
renderer, and native-notification experiment while removing most of the unsafe
lifecycle machinery.

Before adding spawn fallback, require:

  1. Correct and durable attention-event semantics.
  2. A serialized lifecycle coordinator.
  3. A real packaged-repo locator.
  4. Honest attached-versus-owned browser/PWA guarantees.
  5. A server-side bind-before-side-effects fix.
  6. Close/hide/quit behavior rewritten around Electron's actual event order.
  7. Expanded tests and a precise, pinned packaging/signing contract.
